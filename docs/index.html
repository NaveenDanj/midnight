Why Midnight

Every language accumulates syntax it no longer needs — grammar kept for history, punctuation kept for parsers, ceremony kept for habit.

Midnight starts from a plainer question: what does this line of code actually need to say? If a keyword doesn't change the meaning, it doesn't belong. If a concept isn't relevant yet, it shouldn't be on the page.

This isn't about writing fewer characters. It's about removing accidental complexity so the essential complexity — the part that's actually hard — stays visible and honest. Simple programs should read simply. Harder ones should reveal their difficulty on their own terms, not because the language demanded ceremony up front.

Philosophy

I

Syntax earns its place.

Only syntax that carries real meaning survives. Everything else — inherited punctuation, legacy grammar — is a candidate for removal.

II

Power arrives progressively.

Advanced control shows up when you reach for it, not before. A beginner's first program and an expert's hardest one shouldn't look like different languages.

III

Code reads like intent.

Names and structure should say plainly what they do. A reader shouldn't need to decode the syntax before they can understand the idea underneath it.

IV

Complexity is exposed, not hidden.

When a real tradeoff matters — ownership, performance, memory — the compiler should explain it, not hide it and not punish you for finding it.

V

Directness over tradition.

A convention being old isn't a reason to keep it. If a cleaner path exists and loses nothing essential, Midnight takes it.

What makes it different

Structs without repetition

A struct's fields and methods live in one honest block. There's no separate header to keep in sync, no boilerplate constructor to write by hand for the common case. The declaration is the whole story.

Functions that expose the idea

A function's signature reads as what it computes, not as scaffolding around it. Types are visible where they clarify intent, and quiet where they'd just repeat what the code already says.

Control that grows with you

Everyday control flow — if, while, plain assignment — looks plain because it is plain. Systems-level concerns arrive later, when the program actually needs them, not as a tax on line one.

Code examples

A program with nothing to spare

One statement. No entry-point ritual, no imports for a print. The smallest program looks exactly as small as it is.

A struct that carries its own behavior

Fields and methods sit together. Member access reads as plainly as the field names themselves.

person.mn
1struct Person {
2 var string first_name;
3 var string last_name;
4

8}
9
10var Person p = Person{ first_name = "Ada", last_name = "Lovelace" };
11print(p.greet());

Recursion, unadorned

Typed parameters and a typed return say exactly what the function promises. Nothing else is asked of you here.

factorial.mn
1func factorial(int n) int {
2 if (n == 1) {
3 return 1;
4 }
5
6 return n * factorial(n - 1);
7}

A standard library, imported by name

Dotted import paths pull a module's structs straight into scope. No package manifest, no namespace ceremony.

Current state

Midnight is early. It is also already real.

Version 0.1.0-alpha.2 already runs typed functions, if and while, structs with fields and methods, arrays, extern functions, import-based modules with a small standard library, and the primitive types (int, float, bool, string, void). The examples above run as written.

What's missing is still missing on purpose: the language is being built one deliberate piece at a time, in the open, and it will keep changing shape as it grows. Early doesn't mean unfinished in the apologetic sense — it means you're watching the decisions get made.

Governance & RFCs

Language decisions deserve the same restraint as the language itself.

Midnight doesn't have a foundation, a steering committee, or a voting process to point to yet — it's one person's design, made in the open. But syntax is a shared resource: once something ships, everyone who writes Midnight lives with it. So changes that touch the language itself go through a written proposal, not a quiet commit.

01

Open an issue

Describe the problem before the solution. What does the current syntax or behavior get wrong?

02

Discuss it in the open

Alternatives get argued in public, against the philosophy, not around it. A good idea should survive scrutiny.

03

Write the RFC

A short document: the change, the tradeoffs it makes, and the syntax it would add or remove. No feature ships without one.

04

Accept, reject, or reshape

Most RFCs come back changed. That's the process working, not stalling.

As Midnight grows past one maintainer, this process is meant to grow with it — toward shared ownership, not around a single gatekeeper. If you want to shape that, the RFC template is the place to start.

Build from source

shell
git clone https://github.com/NaveenDanj/midnight.git
cd midnight
zig build
./zig-out/bin/midnight run src/data/simple.mn

Requires Zig 0.15.x and LLVM dev tools discoverable via llvm-config (pass -Dllvm-root=<path> on Windows, where llvm-config isn't available). Full instructions in the Getting Started guide.

Get involved

Midnight is built in the open, by whoever shows up.

It's early enough that small contributions still shape the language's direction. Write a program and see where the syntax resists you. Read the compiler and see where the implementation disagrees with the design. Argue for a cleaner way to say something — that argument is exactly what Midnight wants to have.
